Measurement framework

A proposed measurement framework should connect a research result to a useful task. For NSATS Quantum, that means choosing measures appropriate to computation, memory, storage or transfer and recording the complete implementation being compared.

Computation

Define the calculation, its inputs and the usable output. Record task completion time and the resources involved. Where energy is part of the question, account for the relevant processing, memory and movement rather than treating one operation as the entire task.

Computational resources can be recorded as processor time, memory occupied, storage used and energy consumed. Processor time counts time spent executing work; elapsed time also includes periods when a task waits. Memory occupancy can change between stages, so a record should say whether it reports the greatest amount in use or an observation at a particular stage.

Elapsed time describes the duration of a task. Throughput describes the amount of work completed over an observation period. A system handling several jobs together can produce throughput information without establishing how long each job took. A computational assessment can report individual job durations and aggregate throughput as separate measures.

Power is the rate at which energy is used. Energy consumed during a task depends on that rate over the task’s duration, including changes in demand as the work proceeds. A power observation from one stage cannot by itself determine the task’s energy use. The method should identify the quantity actually observed and how it is used in the reported measure.

Storage and memory

Distinguish physical capacity from effective capacity. Temporal compression increases the amount of data stored or retrieved without changing the physical size of the drive: classical data is encoded using quantum-mechanical logic, and reversible computing contributes to compression.

Record the factors governing the increase: the drive, how the licensee uses the technology, and where the licensed gates, buses and computational technologies sit in the licensee’s design. For both existing drives and RAM, record the specially designed classical chipset or controller the licensee adds, built with the licensed technology, to encode data and manage intermediate storage and retrieval. The drive or RAM itself remains ordinary classical storage. This is not a software-only upgrade or a drop-in change; integration is part of the licensee’s design.

Effective capacity depends on processing time, not only physical size. A temporal drive is better described by how much data it can process and store per second than by a fixed capacity.

NSATS sells technology licences, not chips. Its technology helps licensees manufacture their own chips.

For an assessment, describe the information stored or retrieved, the resources used and the time to make requested information available. For RAM, include the running program’s access pattern and the rate at which processors receive data.

Access time describes the delay associated with obtaining requested information. A transfer-rate observation describes the amount of information moved over a stated interval. The application’s pattern of requests affects which observations are relevant. A method can record individual delays as well as the flow over a sequence of requests, instead of substituting one for the other.

The information present when an exercise starts is part of the method. In an ordinary computer, data retained in faster memory from earlier use can have a different access time from data being read from storage for the first time. A record should state how the workload was prepared and whether the same preparation was used for each run.

Networking

Identify both endpoint systems and their quantum-classical network cards, the network route, including the ordinary routers in between, and the dataset. Measure from a defined start to the point at which the receiving application can use the information. This scope includes preparation and reconstruction as well as transmission and receipt.

An application’s useful data and the traffic carrying it are different quantities. Traffic can include control information and repeated transmissions as well as the requested contents. A reported rate should identify which quantity was counted. Otherwise a reader cannot tell whether the measure concerns information delivered for the application or all movement observed on the connection.

Transfers repeated under a workload can take different amounts of time. Reporting only a central value can hide the spread of those observations. The record can retain the individual measurements or describe their variation alongside the summary. Examining unexpected observations under the stated method can distinguish unusual task behaviour from a measurement error.

A reviewable record

Keep the implementation version, comparison configuration, task and conditions with the results. Explain what was measured and how it relates to the intended application. This framework proposes an assessment structure; individual studies need their own defined methods and records.

A comparison configuration is the specified hardware, software and settings used as the reference for the implementation being examined. Its description should identify the choices held constant and the differences deliberately introduced for the comparison.

A measuring instrument or software timer has a resolution: it can distinguish some changes and not others. The reporting method should not suggest more precision than the observation supports. A reviewer needs to know how the measure was obtained, including any calculation applied to the original readings, so the reported result can be traced to what was actually observed.

If the method changes during the work, the record should separate the original plan from what was actually done. An interruption, a changed input or an adjustment to equipment can affect interpretation, even making an otherwise sound observation irrelevant to the original question.
