Reference architectures

A reference architecture shows where a licensed function sits within a system and how it connects to the surrounding components. This page describes NSATS’s licensed functions as reference configurations at the level of responsibilities and interfaces, for a licensee to assess against its own design. NSATS sells technology licences, not chips. Its technology helps licensees manufacture their own chips.

Reference configurations

A reference configuration defines responsibilities and connections for assessment against a licensee’s own design, within the equipment constraints described under Implementation context. An organisation can use a defined reference configuration as an assessment baseline where no existing configuration is available, holding the task, data and operating conditions constant.

Each configuration identifies the task, components, licensed function and exchanges the application observes. Its boundary distinguishes components the licensee builds from existing components and their continuing roles. These descriptions specify no hardware model, version or performance figure.

Hardware implementations use specially designed classical chipsets, not off-the-shelf third-party hardware. Licensed designs can be incorporated into programmable hardware or custom chips. Implementation may use software, programmable hardware or a custom chip; the division depends on the technology and the licensee’s design. NSATS has achieved reversible computing at component level: its swap gates retain input and output information and work reversibly in a limited form. An external processor uses the retained information to regenerate earlier inputs. NSATS describes this arrangement as processor-assisted, semi-reversible computing.

Storage (temporal drive)

Temporal Compression stores or retrieves more original data within a given physical storage resource. The medium can be a hard drive, solid-state drive, USB flash drive, optical medium or an array. The licensee builds and integrates an added, specially designed classical chipset or controller with the licensed technology, connecting storage processing to the host’s software interface. The drive remains ordinary classical storage. This is not a software-only upgrade or a drop-in change.

NSATS’s processor-assisted, semi-reversible computing contributes to compression, so the drive holds more data. Effective capacity depends on processing time, not only physical size. A temporal drive is better described by how much data it can process and store per second than by a fixed capacity.

The application identifies data and submits a storage request through the software interface. The system translates it into operations the device accepts. Returned status distinguishes work awaiting completion, completed work and failure. Intact retrieval is checked against the original data.

Working memory (RAM)

NSATS’s memory technology supports greater usable memory capacity and faster access to working information. Existing classical RAM participates through a specially designed classical chipset or controller added by the licensee and built with the licensed technology. The RAM remains ordinary classical storage. Memory-controller designers have a role alongside RAM manufacturers because access depends on the controller as well as the memory.

The quantum-classical bus carries electrical signals with more than two states, beyond binary 0 and 1. This enables faster processing, data transfer and decision making within a quantum-classical electronic device.

The bus connects memory activity with processors. Requests identify the information by an address and specify the action needed. An assessment considers usable capacity, access time and transfer rate together.

One component for storage and working memory

NSATS’s licensed Quantum technology enables one component to perform both storage and working-memory roles in a solution designed and built by the licensee, while existing drives and RAM remain ordinary classical storage.

The roles remain distinct functions with different access patterns. The licensee determines how they share the component and how it connects to processors and controllers. The same bus carries retained-data and working-data exchanges with processors.

The capacity account treats the roles separately. Four parts are counted separately: retained storage, working RAM, retained gate information and the processor’s working memory.

Networking (paired network cards)

Paired quantum-classical network cards enable high-speed data transfer between systems across a classical network. The licensee builds a card containing a quantum-classical chip for each endpoint, with a connection to its host system. Data passes through ordinary routers.

The network uses ordinary wired, optical or wireless links, including long-distance connections. Compatibility concerns the endpoint systems and the ordinary equipment along the path.

The sending application requests transfer through the host’s networking software. Completion is the point at which the receiving application can use the information. Assessment distinguishes channel capacity, transmitted-bit rate, original-data throughput and elapsed time to usable data.

Security

NSATS’s post-quantum security uses classical computing methods inspired by quantum mechanics. Its protection covers data in transit and at rest and, within chip-based systems, information during processing, in memory and along internal data paths.

For browsers and the servers they connect to, NSATS licenses the security as software under standard software licence terms. The software runs in the browser and on the server. For larger systems, licensees build the security into their own chips.

Assessment covers the applicable implementation and its surrounding system. Protection depends on the cryptographic construction, appropriate key handling and the threat against which it is evaluated.

Versioned records

A versioned record would contain the named software version, supported environment, actual interface contract, file format, error definitions and repeatable verification results. Such records are supplied with the licensed documentation and updates, under the licence. The only software architecture documented so far is the compression demonstration’s session architecture, described on Integration architecture and in the compression documentation.

Responsibilities and interfaces

NSATS licenses its intellectual property: patents, designs and copyrighted software. Where the licensed IP takes the form of software, NSATS supplies it under the licence, with its documentation and updates. Each licensee designs and builds its own solution.

NSATSLicensee
Licensed IP, including gate designs and chip-design technology; licensed software where the IP takes that form, with documentation and updates to that software.Chips, chipsets, controllers, drives, memory, network cards, devices and systems; surrounding software applications and services; integration and evaluation of its own implementation.

Software carries out functions through a program. Programmable hardware allows selected functions to be configured in hardware logic; a custom chip incorporates them into a dedicated design. The choice includes maintenance after deployment and compatibility with other system components. Processing functions need memory and connections whichever route is chosen.

The public interface description covers the networking-software contract for requests and outcomes, the card-to-host path, storage requests and returned status, and bus requests identifying an address and action. Connected components agree on request format, completion and the version of information used. The actual API or command interface, file formats and error definitions for an implementation belong to its documentation supplied under licence.

Co-design considers software and hardware choices together so interfaces, memory use and processing responsibilities fit the application. Verification checks behaviour against requirements. Integration checks examine agreement between components, including request formats, even when each function works on its own. Implementation context describes how a review connects a requirement, its responsible component and its check.

The licensee records the function, components supplying its inputs, application using its result, control of each boundary and existing responsibilities that must continue. Where surrounding equipment already supplies a function, that responsibility remains explicit so evaluation covers the added function and its interaction with existing responsibilities.

Implementation context

In ordinary engineering practice, a reference architecture describes an arrangement of responsibilities that can inform another design. An engineer must assess that arrangement against the constraints of the equipment being designed, including the functions supplied by existing components.

An architecture description and a detailed implementation answer different questions. The description allocates work and identifies the exchanges needed between parts. An implementation must also make choices about the actual software, hardware and connections used to perform that work.

In a design review, a requirement can be traced to the component responsible for satisfying it and the check that will examine it.

Read the implementation and verification guidance and the integration-architecture page for system context.
