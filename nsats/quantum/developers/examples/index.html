Compression examples and tutorials

These guided exercises let readers trace the proposed C demonstration from file selection to restoration, checking what each command is intended to do. They cover the demonstration’s file workflow rather than interfaces for NSATS’s other licensed Quantum technologies. No installation is required: the exercises use design documentation, not executable software, tested source code or recorded test runs.

Commands belong to the proposed interactive prompt, not the operating-system shell. Filenames and the .demo extension are illustrative. Removed bytes remain in the program’s memory, so the reduced file depends on matching session data and is not a standalone backup. Licensed Temporal Compression is described separately.

  • Prepare the reading exercise

    The exercises assume ordinary files, a single running session and unused destination names. Keep the original available so the restored contents can be checked against it. The overview and workflow explain how the output and retained data remain associated as operations proceed.

    Trace the sequence and compare the intended outcomes rather than treating the commands as instructions for software available to run. The checks below concern file contents; they do not promise to preserve permissions, timestamps or other filesystem attributes.

    Technical overview →Workflow guide →

  • Tutorial 1: compress, inspect and restore

    Begin with sample.dat and unused sample-step1.demo and restored.dat destinations. Follow the history through the three requests, keeping the original unchanged and the same session available until restoration is checked.

    StepProposed commandIntended result to check
    Compresscompress sample.dat sample-step1.demoThe new reduced output and its matching session record are both ready before completion is reported; the original remains unchanged.
    Inspectstatus sample-step1.demoIdentify original and current byte counts, completed passes, session availability and whether another pass is permitted.
    Restoredecompress sample-step1.demo restored.datUse the same session to write the original contents to a new destination.

    The restored contents must match sample.dat byte for byte. Equal file sizes alone cannot establish that the original information has been reproduced.

  • Tutorial 2: repeat compression

    Start a fresh example session with sample.dat still available. The unused repeat-step1.demo, repeat-step2.demo and repeat-restored.dat destinations allow files from the first exercise to remain on disk. Each new pass uses the current output while preserving the history’s original size and stopping threshold.

    StepProposed commandIntended result to check
    First passcompress sample.dat repeat-step1.demoStart a new history for this exercise.
    Second passcompress repeat-step1.demo repeat-step2.demoUse the first output and retain the same original size and threshold.
    Inspectstatus repeat-step2.demoAccount for both completed passes.
    Restoredecompress repeat-step2.demo repeat-restored.datReproduce the original contents using the latest output and matching data from both passes.

  • Follow the byte counts

    Removing 3% from an illustrative 1,000,000-byte original leaves 970,000 bytes. Removing 3% from that output leaves 940,900 bytes, with 59,100 removed bytes retained in session data before encryption, padding and metadata overhead. Planned pass percentages vary; the figures illustrate arithmetic rather than a fixed setting or measured performance.

    A complete resource assessment also counts retained files and working memory. A smaller current output alone does not establish lower total storage use, because the information needed to restore it remains elsewhere in the workflow.

  • Account for resources before restoration

    Pause after the status request in Tutorial 2. If the original and both outputs remain on disk, they occupy 1,000,000 + 970,000 + 940,900 = 2,910,900 bytes. The live session additionally retains at least 59,100 removed bytes before encryption, padding and metadata overhead; peak working memory is not specified.

    A restored copy adds another 1,000,000 bytes on disk. The draft does not define what happens to session data after successful restoration, so neither retention nor disposal should be assumed. Temporary files and other working memory also belong in an assessment. These counts describe the illustrative demonstration, not the capacity or performance of licensed NSATS technology.

    Review total-workflow resource accounting

  • Tutorial 3: limits, failures and unavailable data

    The stopping threshold defines the remaining output size the reduced file may reach. It is selected once for an original history and is not a target amount of removed data. Giving an output a different name does not reset it. The situations below distinguish a permitted stopping point, invalid data, loss of a session and a failure handled while the session remains available.

    SituationIntended responseWhat remains possible
    The permitted compression limit is reachedExplain the limit and leave the current output unchanged.Restore with intact matching session data.
    The session ends after a reduced output is createdA new session refuses restoration: “No matching session data is available.”Use the preserved original as the recovery source.
    Verification detects a changed reduced outputReject the operation without reporting successful restoration.Keep the original; do not use an unverified result as completed output.
    The requested destination already existsRequest another destination under the proposed no-overwrite policy.Choose an unused path without overwriting the input or original.
    A read, memory-allocation or write failure is handled in the live sessionReport the failure and preserve the last valid output and matching session data.Continue only under defined retry/cancellation rules; partial output is not complete.

    No fixed pass count or final byte count is prescribed. Rounding, the final pass, filename quoting, empty files and other boundaries need an implementation contract. The exercise leaves those decisions open rather than assigning behaviour the draft has not defined.

  • Exercise: distinguish two file histories

    Consider two different original files in one running session. Each has its own original size, stopping threshold, completed steps and restoration data. An additional pass for one history must not change the progress recorded for the other.

    Trace a status request for each current output and identify the history it describes. Restoration must pair that output with its own matching data; a filename alone cannot establish the association. The exercise can be completed without choosing rules for older, renamed or copied outputs, which remain unresolved.

    compression input requirements

  • Turn the exercises into review findings

    The reading exercise should identify whether the documented operations, session responsibilities and expected outcomes agree. Any unclear condition can be recorded as a design question and checked against the command reference or integration guide.

    Assessing an implementation would additionally require an identified version, environment and observed results. The testing guidance describes how to plan those checks; completing the reading exercises does not establish that software has passed them.
