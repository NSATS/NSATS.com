Examples and tutorials

Explore illustrative magnetometer response records, a per-channel averaging example and eight guided documentation exercises covering acquisition and equipment operation. These design-reading examples are neither measured device data nor simulation results, and do not define how positioning is computed.

In engineering work, simulated data comes from a model, while measured data comes from observing equipment or a process. A result’s origin affects which question it can answer and how it should be interpreted.

Magnetometer design examples

The magnetometer software development kit (SDK) documentation provides illustrative response records and a worked averaging example.

SDK design documentation. Draft 2 · 9 October 2026

The records show eight separate channel slots, missing-data handling, calibration results and self-test outcomes. The arithmetic example reports included, rejected and missing observations for each channel and withholds a mean when too few observations are usable.

These are illustrative structures and educational arithmetic, neither measured device data nor results from a simulation. They supply no executable example and do not show how positioning is computed.

Guided magnetometer exercises

These are reading exercises for the interface design. Use the command reference alongside the walkthrough; no equipment or executable software is supplied by these exercises. The records are illustrative structures, and the averaging calculation uses arbitrary example units. They are neither measured device data nor simulation results.

Exercise 1: connect and log in

You need the connection and login explanation. Trace connect DEVICE_REFERENCE followed by login in a scenario with a supported adapter and device authentication mechanism.

Communication can be established while access remains unauthenticated. Confirmed device authorisation is needed before a protected operation. A rejected login supplies no protected result; credentials belong in the supported protected prompt or provider, not in example commands or logs.

You should be able to explain why connection alone grants no authority. Read the login example.

Exercise 2: inspect and read eight channels

You need the eight-channel description and sufficient access in the illustrative scenario. Trace describe, then read once channels=all.

Check for eight separate entries, each with its own payload and status. A1–A8 are documentation aliases, not physical connector labels. Representation, units and timing must come from the device description; they remain unknown until specified.

You should be able to identify the information needed to interpret each channel. Read the first-reading step.

Exercise 3: recognise a partial acquisition

You need the acquisition record explanation. Consider read once channels=all returning valid entries for A1–A7 and no usable result for A8.

The acquisition remains partial. A8 is unavailable, not zero, and an unknown sample time stays unknown rather than becoming the computer's receipt time.

You should be able to distinguish a missing observation from a measured zero. Read the eight-channel response structure.

Exercise 4: inspect and select DSP

You need the processing-profile requirements. Trace dsp inspect PROFILE_REFERENCE before dsp select PROFILE_REFERENCE.

Check the signal representation, processing location, parameters and effective configuration revision. An unavailable profile is reported as unsupported; a different filter must not be substituted silently. Preserve access to raw input where supplied, or identify when the device supplies only processed data.

You should be able to state what must be known before selecting a profile. Read the DSP operations.

Exercise 5: average each channel separately

You need the averaging explanation. Trace average configure METHOD WINDOW_REFERENCE followed by read window channels=all. The command form leaves input-stage and per-channel-scope parameters to the implementation contract.

For this arithmetic exercise only, use a four-observation window with at least three included observations. Average within each channel; do not combine channels by default.

ChannelIntended resultIllustrative observationsIncludedRejectedMissing
A1Mean 1210, 12, invalid, 14310
A3Insufficient data; no mean30, missing, missing, 36202

For A1, (10 + 12 + 14) / 3 = 12. Do not replace the invalid observation with zero. A3 has fewer than three included observations, so a numeric mean would violate this example's policy. No physical units, sampling rate or SDK default are assigned by the calculation.

You should be able to reproduce A1's result and explain why A3 has none. Read all eight example rows.

Exercise 6: distinguish calibration targets and application

You need the calibration operation reference. Trace calibration inspect, calibration prepare TARGET PROCEDURE_REFERENCE, calibration run PLAN_REFERENCE and calibration apply RECORD_REFERENCE.

Antenna calibration and DSP signal-source calibration have different targets and records. A successful run produces a candidate; applying it is a separate request requiring confirmed scope and authority. Keep EXAMPLE_ANTENNA_CAL distinct from EXAMPLE_SOURCE_CAL. Do not infer a universal rollback operation.

You should be able to distinguish an available candidate from an applied record and explain why one calibration cannot replace the other. Read the calibration example.

Exercise 7: interpret radio equipment self-tests

You need the equipment self-test explanation. Trace selftest list and then selftest run TEST_REFERENCE for a procedure whose prerequisites and acquisition impact are known.

Operation completion and equipment-check outcomes are separate. A completed request may contain a failed check and another check that was not run. Keep pass, fail, not run, unsupported and inconclusive results distinct, and inspect the device state before returning to acquisition. A connection check is not a radio self-test.

You should be able to read a mixed result without calling the equipment passed. Read the self-test example.

Exercise 8: communication loss during a hardware change

You need the result conventions. Consider a connection dropping during calibration apply RECORD_REFERENCE.

Report outcome unknown and do not repeat the request automatically. After reconnecting, authenticate as required and inspect with describe and calibration inspect. These are inspection routes, not guaranteed readback of whether the operation completed. The hardware contract must supply the recovery steps and evidence needed to resolve the state.

You should be able to explain why a lost connection or timeout during a hardware change leaves the outcome unknown. Read the failure examples.
