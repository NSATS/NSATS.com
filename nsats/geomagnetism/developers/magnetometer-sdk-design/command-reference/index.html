Magnetometer SDK: command reference

Design documentation. Draft 2 · 9 October 2026

The magnetometer software development kit (SDK) interface design identifies the operations an application would request, the conditions required before each operation and the information expected in its response. An implementation could expose these operations through a command utility or programming interface once the device protocol is defined.

The names below are illustrative design forms, not released software interfaces or actual hardware commands. Uppercase terms represent values supplied for a particular device or procedure.

Session and acquisition

OperationPrerequisiteIntended result
connect DEVICE_REFERENCEA supported adapter and device reference.Connection result, available identity and unauthenticated access state.
loginA live connection and specified authentication mechanism.Confirmed access state and permissions, or an access failure.
describeSufficient access for device inspection.Device/adapter versions, channel mapping, supported functions and active configuration.
read once channels=allAuthorised measurement access and an interpretable channel contract.One acquisition with eight channel entries and their statuses.
read window channels=allThe above plus valid window and processing settings.An acquisition window and separately identified processing results.
stream start channels=allSupported continuous acquisition and defined rate/buffering settings.Stream identifier and confirmed effective settings.
stream stopAn active stream.Whether stopping was confirmed and the disposition of any final partial data.
logoutAn authenticated session.Access revocation outcome and local credential cleanup status.
disconnectA connected or failed session.Local connection closure and any unconfirmed equipment state.

The implementation specification must define stream delivery, buffering and overflow handling. The request stream start channels=all does not establish how those behaviours work or guarantee that continuous acquisition is supported.

Measurement and configuration requests must be rejected when the required authorisation is absent. If the equipment has no authentication facility, its access model must be resolved explicitly; the application must not represent a simulated login as successful hardware authentication.

Digital signal processing (DSP) and averaging

OperationPurposeInformation returned
dsp inspect PROFILE_REFERENCEInspect a documented processing profile before use.Applicable signal type, parameters, input/output representations and execution location.
dsp select PROFILE_REFERENCERequest the selected profile.Accepted configuration or a reason for rejection; no silent parameter substitution.
average configure METHOD WINDOW_REFERENCESelect an averaging policy for each channel.Effective window, input stage, method parameters, validity rules and configuration reference.

The averaging configuration must identify both the input stage and the channels to which it applies. The illustrative form average configure METHOD WINDOW_REFERENCE leaves those parameters unspecified, so the implementation must define how they are supplied.

Selecting a profile does not establish that every named method is supported. Confirm the effective settings and, where a change takes effect at a later sample boundary, identify that boundary. Changes to configuration, calibration or session continuity must reset affected processing history according to the selected profile.

Calibration

OperationPurposeInformation returned
calibration inspectInspect existing calibration and available procedures.Antenna and DSP signal-source records, scope and applicability.
calibration prepare TARGET PROCEDURE_REFERENCECheck requirements for a specific calibration.Plan reference, affected channels or sources, required reference and acquisition impact.
calibration run PLAN_REFERENCECarry out a supported prepared procedure with suitable authority.Progress and a candidate calibration record, or failure/unavailable status.
calibration apply RECORD_REFERENCEExplicitly request application of a reviewed candidate.Confirmation, scope, persistence and effective configuration revision.

TARGET identifies either antenna channels or a DSP signal source. These are different calibration targets and require separate records. Producing a candidate record does not apply it to the hardware; application requires an explicit request with the appropriate authority.

Restoring an earlier calibration also depends on a recovery procedure supported by the device. The interface design does not define a universal rollback command.

Radio equipment self-tests

OperationPurposeInformation returned
selftest listDiscover or inspect documented available equipment tests.Test scope, prerequisites and whether measurement or a signal source is affected.
selftest run TEST_REFERENCERequest one permitted, supported test.Operation status and per-check results from the defined test procedure.

Only supported equipment tests may be requested. If the required capability is unavailable, report that limitation rather than substituting a software-only check and presenting it as a successful radio equipment test.

Result conventions

Each result must identify the request, device, session and configuration concerned. Completion of an operation is separate from the outcome of its individual checks: a self-test request can complete while an equipment check fails.

The design retains eleven failure categories: not connected, authentication required, authentication rejected, access denied, unsupported operation, invalid configuration, missing calibration, timeout, partial acquisition, invalid sample and outcome unknown. These describe behaviour; exact error codes and device messages belong to the implementation specification.

A timeout during an operation that changes hardware leaves the outcome unknown until it is resolved. It does not establish that the change failed or stopped. The same distinction applies when communication is lost during calibration, source activation or another hardware change.

Do not repeat an uncertain hardware-changing request automatically. Use describe, calibration inspect and selftest list to inspect the available configuration, calibration and procedure information. These operations do not guarantee retrieval of the interrupted operation’s completion status; recovery must follow the device’s documented procedure. Retried read requests also need identifiers so duplicate responses are not counted as separate observations.
