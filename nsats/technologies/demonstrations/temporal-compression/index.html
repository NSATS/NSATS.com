Temporal Compression demonstration

How to use the demonstration

  1. Choose a scenario and read its task.
  2. Select the supplied sample or the prepared receipt associated with the required record.
  3. Follow the illustrated stages. Received means the example file has been accepted; Stored means its illustrated storage operation is complete.
  4. Use the sample receipt to fetch the file from the website and check its fingerprint.
  5. When the required comparisons match, choose Save file to keep a copy.

You can copy the sample code and save the example receipt. If you want to compare a local copy afterwards, choose Check a saved copy. Your browser checks the file you select locally and reports whether that selected copy matches.

The temporal drive

Temporal Compression uses concepts from quantum mechanics to store more data within a given physical storage resource. NSATS has developed a specific hard drive using quantum-mechanical logic as its own research and development (R&D) demonstration of its licensed technology. In a licensee's implementation, existing drives remain ordinary classical storage. The licensee adds a specially designed classical chipset or controller built with the licensed technology. It encodes the data and manages the intermediate operations when information is stored or retrieved.

NSATS licences enable classical devices to perform operations based on quantum mechanics, at room temperature.

Physical capacity describes the storage resource a device contains. Effective capacity describes how much data is stored within it.

Effective capacity depends on processing time, not only physical size. A temporal drive is better described by how much data it can process and store per second than by a fixed capacity.

The increase in effective capacity depends on the drive, how the licensee uses the technology and where the licensed components sit in the design.

Temporal Compression applies to both retained storage and working RAM. A drive retains information for later retrieval, while RAM holds data used during computation. This demonstration concerns retained file storage: the file is requested again when it is needed.

NSATS sells technology licences, not chips. Its technology helps licensees manufacture their own chips.

The file journey

How the file service is designed to work

The file service is designed to accept a file sent to NSATS over a secure HTTPS connection. After accepting the complete file and confirming its fingerprint, NSATS would issue a random 256-bit tracking code with a Received status. The storage operation would then reach Stored, or report Failed if it could not complete. You would keep the code with the record identifying why you stored the file.

When you needed the file, you would submit that code. NSATS would decompress the stored file and make it available as a download. You would compare its fingerprint with the original to check that the returned contents matched.

What this illustration does

When you select a sample, your browser reads it and calculates a fingerprint. The walkthrough illustrates acceptance, a SAMPLE receipt and the transition to Stored. Some time later advances that sequence without representing a measured processing time.

At retrieval, the browser fetches the sample from this website and calculates its fingerprint again. For a newly selected sample, it compares this with the value calculated at selection. A retrieval-first task instead uses the expected fingerprint included in its prepared example receipt. The result names the source it used.

This lets you practise reading a receipt and checking a returned file. Evaluation of a temporal drive's capacity and processing belongs to an implementation assessment with its own measurements and conditions.

Reading the sample receipt

The receipt connects a sample code with a file and its expected contents. Its SAMPLE label remains visible when you copy the code or save the receipt. Sample codes use a short format accepted only by this walkthrough, distinct from the intended service's code format, and are never placed in a web address.

Receipt fieldWhat it helps you identify
Sample codeThe example file to request in this walkthrough.
File nameThe sample associated with the receipt.
File sizeThe size of that sample, read from the file.
FingerprintA SHA-256 value used to compare the file's contents.
Fingerprint sourceWhether the expected value came from your sample selection or a prepared example receipt.
Illustrated storage statusWhether the example is Received, Stored or Failed.

The intended service's 256-bit tracking code and a file fingerprint have different purposes. The code is a reference used to request the file. The fingerprint supports a comparison of file contents. 256-bit describes the code's size in bits; the displayed code is a readable representation of that value.

Find the right maintenance record

A pump's maintenance log contains separate entries for a seal replacement, a bearing failure and a later inspection. Begin with the prepared receipts and select the one attached to the bearing-failure entry. Fetch its sample file and compare it with the fingerprint included in that receipt, then save the matching file.

Retrieve the revision required by a design review

A design review register calls for revision B, while sample receipts are available for revisions B and C. Start by retrieving C. Its contents can match its own receipt while still differing from the revision expected by the review register.

Read both comparisons: Matches this receipt and Matches the required revision. Then choose B and repeat the check. When both comparisons match, select Save file to complete the task.

Send the original document, then retrieve it

An example document library contains an original and an edited copy with the same file name. Start in Store a sample, choose the edited copy and select Send (illustrated). Keep its SAMPLE receipt, advance to Stored, then retrieve and check the file you selected.

The fetched file matches its own receipt, but the comparison labelled Expected by the example document library shows that it differs from the original. This is a mistake in the sender's file selection: the walkthrough returns the edited copy that was selected.

The lesson for the intended service is: The service returns exactly what was sent, so make sure you send the original.

Reading the result

Received and Stored answer different questions. Received records acceptance of the complete example file with its fingerprint confirmed. Stored records completion of the illustrated storage operation. A tracking code at Received therefore identifies the submission before it is ready for retrieval.

At retrieval, the browser compares the full calculated fingerprint with the stated expected value. A match supports the conclusion that the fetched sample has the expected contents. In revision and original-document tasks, read the additional application comparison before deciding that you have the required file.

Save file becomes available when the scenario's required comparisons match. Your browser then handles the download. The optional local check reports The selected copy matches if the file you subsequently select has the expected contents.

Example failure branches carry their own labels, such as Example interruption or Example mismatch. The browser's actual fetch and comparison result remains separately identified, so you can distinguish the selected teaching example from the check performed on the sample.

Files used in this walkthrough

Use the prepared sample named by your task. File sizes and fingerprints come from those files, and the receipt keeps the relevant values together. The optional saved-copy check reads the file you select within your browser.

If a sample cannot be fetched or its fingerprint check cannot complete, the result explains the problem and offers the relevant retry. A successful check of a website sample concerns that file; capacity and processing measurements require a separate technology evaluation.

Returning to a sample

If an older sample receipt is no longer recognised, choose a current prepared example. Reopening the walkthrough starts from its available examples; it does not promise to preserve an earlier tab's progress.

For developers and evaluators

Start with the file journey your application needs: identify the input, retain the reference and expected fingerprint, read the storage state, then compare the returned file before passing it to the next task. Keep the application's expected document or revision separate from the receipt's record of the file actually selected.

For a licensed implementation, evaluate storage and retrieval with stated conditions and measurements. The Temporal Compression technology page and Quantum readiness guidance provide the wider context; licensing evaluation supports preparation for an implementation discussion.

Questions

What does a sample code retrieve?

It selects the website sample associated with an example receipt. The receipt's SAMPLE label identifies the illustration.

Why can I have a receipt before the file is Stored?

The file service is designed to issue a receipt after complete-file acceptance and fingerprint confirmation. Storage then has its own outcome. The illustration makes those stages separate so you can read them correctly.

Is a matching fingerprint enough to choose the right document?

It tells you whether contents match the expected fingerprint you used. The revision and original-document scenarios add a comparison with the application's required file, because a correctly returned copy may belong to a different revision.

Can I check a saved sample?

Yes. Select it through Check a saved copy. The local comparison reports whether that selected file matches the expected contents; the file stays in your browser.

What if I return without my sample receipt?

Choose one of the prepared example receipts. The maintenance task also shows why an application's own record needs to retain its file reference.

Where can I learn about capacity and implementation?

Read the technology and evaluation pages, then use the licensing route to describe your intended application and the questions you need to evaluate.
