Testing and evaluation planning

A useful test plan begins with the function an application expects. The approach below sets out questions for evaluating a licensee’s implementation of NSATS technology, from correct operation to performance within a complete task.

Describe expected behaviour

Describe expected behaviour so that integration can be assessed alongside the normal processing path. Include:

  • The inputs.
  • The result and the conditions in which the operation is used.
  • For multi-stage tasks, what each stage supplies to the next.
  • The behaviour needed when a request cannot be completed.

A test case combines a selected situation with an expected outcome established from the application requirement.

For a multi-stage task, a check can capture a stage’s output before the next stage uses it and compare it with the expected intermediate result. A correct intermediate value followed by an incorrect final result directs attention to later work; an incorrect intermediate value identifies an earlier discrepancy. Checking only the final output can leave that distinction unresolved.

Some inputs sit close to the limit of a permitted condition. A check at such a boundary examines whether the application changes behaviour in the required place. Cases clearly inside the permitted range do not answer the same question. The plan can identify boundaries in the application requirements without assuming which of them will be difficult for the implementation.

Select representative work

Choose data and tasks that reflect the intended application. A memory evaluation needs relevant access patterns; a networking evaluation needs defined sending and receiving systems. Preserve the configuration with the test record so that another reviewer can understand what was assessed.

Representative work includes the patterns that matter to the intended use, rather than only inputs that are easy to obtain. A collection dominated by ordinary cases can leave unusual but permitted situations unexamined. The test plan should state how cases were selected and which application behaviours that selection covers. Uncovered situations remain identifiable questions for the assessment.

Workload selection also concerns the order of actions. Individually valid tasks may share resources when they overlap, or leave information that affects later work. A developer can choose sequences drawn from the intended application and describe what other activity is present.

Separate function and performance

First establish what the implementation does for the selected task. Then examine time, capacity, transfer rate or energy as appropriate. Compare against a defined reference, repeat the work under recorded conditions and retain enough detail to interpret the results. This is a proposed evaluation framework for discussion.

Repeating a task can reveal variation between runs. A record should retain that variation rather than select only an unusually favourable observation. If a run is excluded, the reason should be recorded with the observations. The intended method should distinguish a repeat under the same conditions from another exercise in which the conditions have deliberately changed.

A check can also produce an outcome that cannot yet be interpreted. The observer may be unable to determine whether the required behaviour occurred or whether the measurement was usable. Such a case can remain unresolved while its cause is investigated. That is different from recording a successful test, and it preserves the question the assessment still needs to answer.

Plan checks for the compression demonstration

The following checklist translates the compression documentation into proposed checks for a future implementation. It records expected behaviour, not tests already performed.

CaseExpected behaviour to verify
One pass and restorationA new reduced output and matching session data are created; restored contents match the original byte for byte.
Repeated passesEach pass uses the current output; restoration accounts for every completed pass and reproduces the original.
Multiple file historiesEach current output remains associated with its own original and session records.
Compression limitFurther compression stops while restoration remains available with intact session data.
Changed output or mismatched historyVerification rejects invalid association or changed data without reporting successful restoration.
Existing destination or path aliasThe input, original and existing destination are not overwritten under the proposed policy.
Read, allocation or write failure handled in a live sessionThe last valid output and matching session data remain usable; partial output is not reported as complete.
Process terminationA new session cannot restore an earlier reduced output without its lost session data.

For each check, record the implementation version, environment, starting files, operation sequence, expected outcome and observed result. Do not mark a case as passed before running it. Empty files, byte rounding, the final pass, cancellation and retry details require a precise implementation contract before their expected outcomes can be fixed.

Count all retained disk files and working memory when assessing resources. These checks concern the demonstration; they do not establish licensed technology performance.
