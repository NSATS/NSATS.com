Compression examples and tutorials

Work through the compression and restoration design using the guided exercises below. Each exercise identifies its starting conditions and intended result. The documentation covers the compression demonstration’s file workflow only; it does not describe interfaces for NSATS’s other licensed Quantum technologies.

SDK design documentation. These are reading exercises for the proposed C software demonstration. They are not execution transcripts or tested source code. Commands belong to the demonstration’s proposed interactive prompt, not the operating-system shell. The filenames and .demo extension are illustrative.

This software demonstration holds removed bytes in the program’s memory; Temporal Compression is explained on its technology page.

  • Before starting

    Read the overview and workflow. The examples assume ordinary files, a single running session and unused destination names. Keep the original file available. The reduced output depends on its session data and is not a standalone backup.

    For this reading exercise, trace the commands and compare the described outcomes. No software installation is needed to work through the documentation.

    Technical overview →Workflow guide →

  • Tutorial 1: compress, inspect and restore

    The purpose is to follow one file history from its original input to a restored copy. Begin with sample.dat and unused sample-step1.demo and restored.dat destinations.

    StepProposed commandCheck the intended result
    1. Compresscompress sample.dat sample-step1.demoThe original stays unchanged; the new reduced output and its matching session record must both be ready before completion is reported.
    2. Inspectstatus sample-step1.demoIdentify the original and current byte counts, completed passes, session availability and whether further compression is permitted.
    3. Restoredecompress sample-step1.demo restored.datUse the same session to write the original contents to a new destination.

    Compare every restored byte with sample.dat. Matching sizes alone do not establish success. This exercise concerns file contents; it does not promise preservation of permissions, timestamps or other filesystem attributes.

  • Tutorial 2: repeat compression

    Start a fresh example session with sample.dat still available. Use the unused repeat-step1.demo, repeat-step2.demo and repeat-restored.dat names; the first exercise’s files may remain on disk.

    StepProposed commandCheck the intended result
    1. First passcompress sample.dat repeat-step1.demoStart a new history for this exercise.
    2. Second passcompress repeat-step1.demo repeat-step2.demoUse the current output; retain the history’s original size and stopping threshold.
    3. Inspectstatus repeat-step2.demoAccount for both completed passes.
    4. Restoredecompress repeat-step2.demo repeat-restored.datRestore the original contents using the latest output and matching data from both passes.

    Work through the byte counts

    As an arithmetic illustration, removing 3% from 1,000,000 bytes leaves 970,000 bytes. Removing 3% from that output leaves 940,900 bytes. The 59,100 removed bytes are retained in session data before encryption, padding and metadata overhead. Actual planned percentages vary; these figures are not measured performance or a fixed setting.

    A total-workflow assessment also counts the original, earlier outputs, restored copies and temporary files on disk, plus session data and peak working memory. A smaller current file alone does not establish lower total storage use.

    Account for resources before restoration

    Pause after the status step of Tutorial 2, before requesting restoration. If the original and both outputs are retained, their disk use is 1,000,000 + 970,000 + 940,900 = 2,910,900 bytes. The running session also holds at least 59,100 removed bytes before encryption, padding and metadata overhead, with peak working memory still unspecified.

    A restored copy would add another 1,000,000 bytes on disk. The treatment of session data after successful restoration remains undefined, so do not assume that it is retained or discarded. This is illustrative accounting for the demonstration, not a performance measurement of licensed NSATS technology.

    Review total-workflow resource accounting.

  • Tutorial 3: recognise limits and unavailable data

    The stopping threshold is the remaining output size selected once for an original file’s history. It is not a target for the number of removed bytes. Giving the next output a new name does not reset the threshold.

    Situation to traceIntended responseWhat remains possible
    The permitted compression limit has been reachedA further compression request leaves the current output unchanged and explains the limit.Restoration remains available with intact matching session data.
    The session ends after a reduced output is createdA new session refuses restoration and reports: “No matching session data is available.”The preserved original remains the recovery source.
    Verification detects a changed reduced outputReject the operation without reporting successful restoration.Keep the original and do not use an unverified result as a completed output.
    The requested destination already existsRequest a different destination under the proposed no-overwrite policy.Choose an unused name without overwriting the input or original.
    A read, memory-allocation or write failure is handled while the session remains runningReport the failure and preserve the last valid output and matching session data.Do not treat a partial output as completed; retry and cancellation rules still need an implementation contract.

    No final byte count or fixed pass count is prescribed. Rounding, the final pass, path quoting, empty files and other boundary cases need an implementation contract before executable exercises can cover them.

  • Exercise: keep two file histories separate

    Read the compression input requirements, then consider two different original files in the same live session. Each starts its own history with an original size, stopping threshold and completed steps. An additional pass for one history must not change the other's progress.

    Trace a status request for each current output and identify which history it describes. Restoration must use the matching output and session data for that history; a filename alone does not establish the match. You should be able to explain how the two histories remain independent without choosing rules for renamed, copied or older outputs that the draft leaves unspecified.

  • Continue into integration and testing

    Use the command reference to check each operation’s conditions. The integration guide explains session ownership, sequencing and failure handling. The testing page provides a proposed verification checklist for a future implementation.
