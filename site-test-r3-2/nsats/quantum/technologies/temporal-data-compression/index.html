Temporal Compression

NSATS’s temporal compression technology uses concepts from quantum mechanics to store more data within a given physical storage resource. A licensee integrates the technology into its storage system through a specially designed classical chipset or controller.

Physical and effective capacity

Physical capacity describes the storage resource a device contains. Effective capacity describes how much data is stored within it. Temporal compression increases effective capacity while the drive’s physical size stays unchanged. Classical data is encoded using quantum-mechanical logic, and reversible computing contributes to compression.

Effective capacity depends on processing time, not only physical size. A temporal drive is better described by how much data it can process and store per second than by a fixed capacity.

The increase depends on the drive, how the licensee uses the technology and where the licensed gates, buses and computational technologies sit in the licensee’s design. This distinction matters when space for drives is limited and the information to retain keeps growing: greater effective capacity lets the available storage hold more of that data.

A storage budget includes the drive itself and the equipment needed to connect and power it. Adding a drive can require an available connection, space in an enclosure and provision for its electrical and cooling needs. The amount of data an application needs to keep and the equipment space available to it are therefore different entries in a system specification.

Storage and retrieval

Existing drives and RAM remain ordinary classical storage. The licensee integrates an additional, specially designed classical chipset or controller built with the licensed technology. It performs the encoding described above and manages the intermediate processing when compressed data is stored or retrieved. This is not a software-only upgrade or a drop-in change; integration is part of the licensee’s design. The application determines what to store, which information to request and how to use the returned data.

In an ordinary storage system, a program requests a particular file or piece of information through a software interface. The system translates that request into operations the storage device can accept. A storage controller coordinates access to the medium and the transfer of data to or from the computer. The application works with requests and returned information rather than issuing every device-level command itself.

An ordinary software interface can distinguish a request that is still pending, one that completed and one that failed. The calling program uses that status to decide whether to continue dependent work or handle an error. Submitting a request alone does not tell the program that the requested work has finished.

Storage and working memory

A drive retains information for later use, while RAM supplies working data to running programs. Temporal compression applies to both, with different demands on access. Through the licensee’s added chipset or controller, high-speed RAM holds the encoded classical data so computer buses can send and retrieve it faster.

These internal connections include the quantum-classical bus, which carries electrical signals with more than two states, beyond binary 0 and 1. This enables faster processing, data transfer and decision making within a quantum-classical electronic device.

Usable capacity is weighed alongside access time and the rate at which data reaches processors. The intended task determines how these requirements fit together.

An interactive program may ask for an individual item and then wait before it can carry on. A program reading a collection in sequence can request successive portions as part of one continuing task. The first pattern makes the delay associated with each request significant; the second also depends on sustaining the flow of information. A storage assessment should use the application’s actual pattern of requests, including what the program does between them.

Applications

Archives and retained information

An archive keeps information so that it can be retrieved later. Temporal storage increases the amount held within the available drive capacity. This application concerns systems with growing collections of data, where the storage requirement is shaped by both the volume retained and the need to retrieve individual information when required. In data centres, fewer hard drives and less memory are needed to store data, and the chipsets run with lower heat than conventional computing.

In an illustrative archive of engineering drawings, a user may request the drawing for a particular component while the rest of the collection remains stored. The catalogue identifies the requested record, and the storage system supplies its contents. In a data centre, the storage footprint includes the drives and enclosures holding collections; working memory is occupied by the programs and active data used to search and serve them.

Systems that collect data continuously

Systems that collect information continuously need somewhere to retain each new addition. Temporal storage helps them hold more of that accumulated data within the drive capacity available. The licensee’s chipset or controller handles storage and retrieval, while the application determines which information to request for later analysis or other use in the system.

In an illustrative environmental monitoring system, observations arrive from sensors while an analyst requests readings from a particular sensor. The collection task adds records; the analysis task selects the records it needs. These activities can place demands on the same storage system at the same time. An application specification should distinguish incoming data from data requested for analysis and state which work must continue during those requests.

Storage-system implementation

A storage implementation places these functions within the surrounding device or system. The design needs to account for the physical storage available and the path between the application and the licensee’s chipset or controller.

The software interface specifies how a program identifies data and submits a storage request. The physical connection carries the corresponding signals between devices. These are separate parts of integration: software must issue a request the device recognises, and the connected components must be able to exchange it.

Evaluation can consider the amount of data stored, the time taken to store and retrieve it, and the accuracy of the returned information. These measures relate effective capacity to the application’s practical storage requirements.

An evaluation record can state what information was supplied, what was requested and what was returned. For an application-level timing measurement, the start and end points can be the submitted request and the completion reported to the program. Checking returned information against the supplied material tests correctness. A completed transfer alone does not show that the application received the information it requested.

IP licensing

NSATS licenses the intellectual property for incorporation into licensee designs. NSATS sells technology licences, not chips. Its technology helps licensees manufacture their own chips. A discussion can begin with the type of information to be stored, the physical storage available and the way the application needs to access its data.

Describe the collection in application terms: for example, records identified individually or datasets usually read as a whole. Include whether the application adds information while other work requests existing records, and which software and equipment the design must connect to. A licensee can also identify the data it would use to evaluate those requests and the outcome each operation should produce.
